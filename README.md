# Лабораторная работа №4: Аутентификация, авторизация и Swagger

## 📌 Цель работы
Завершение бэкенда для SPA: реализация аутентификации через сессии (Redis), разграничение ролей (клиент / модератор), подключение Swagger (OpenAPI) и подготовка документации.

## 🛠 Технологии
- **Backend**: Django, Django REST Framework, `django_redis`, `drf-spectacular`
- **Хранилище сессий**: Redis (база №1)
- **База данных**: PostgreSQL (основные данные)
- **Документация API**: Swagger UI
- **Тестирование**: Insomnia, Swagger, curl

## ✅ Выполненные задачи

### 1. Аутентификация через сессии
Реализованы методы:
- `POST /api/bank_users/register/` – регистрация
- `POST /api/bank_users/login/` – вход (выдаёт `sessionid` в cookie)
- `POST /api/bank_users/logout/` – выход

Сессии хранятся в Redis (`SESSION_ENGINE = 'django.contrib.sessions.backends.cache'`).

### 2. Разграничение прав (роли)
- У модели `User` добавлено поле `is_moderator`.
- **Гость** – может только просматривать услуги (`GET /bank_services/`).
- **Клиент (создатель заявки)**:
  - Может создавать черновики, добавлять услуги, изменять ФИО, формировать заявки.
  - Просматривает только свои заявки.
  - Не может завершать заявки (403 Forbidden).
- **Модератор**:
  - Видит все заявки.
  - Может завершать/отклонять заявки (PUT `/complete/`).

### 3. Автозаполнение `created_by`
При создании черновика (`POST /bank_request_items/add/`) поле `created_by` автоматически проставляется текущим авторизованным пользователем.

### 4. Swagger (OpenAPI)
- Подключён `drf-spectacular`.
- Документация доступна по адресу: `/api/swagger/`.
- Настроены схемы безопасности (сессионная аутентификация).
- В Swagger отображаются все методы, сгруппированные по доменам.

### 5. Тестирование через Insomnia
- Сессионная кука `sessionid` копируется из браузера (после логина в Swagger) и вставляется вручную в заголовок `Cookie` в Insomnia.
- Продемонстрированы:
  - `401` для неавторизованного GET `/requests/`.
  - `403` для клиента при попытке завершить заявку.
  - `200` для модератора при завершении.

### 6. Проверка Redis
- Через `redis-cli` получен список ключей сессий (`KEYS *`).
- С помощью Python (Django shell) выполнена десериализация сессии и получен `_auth_user_id`, что доказывает соответствие сессии конкретному пользователю.

### 7. Документация
- Оформлен РПЗ (титульный лист, 3 диаграммы, расчёт аппаратных требований).
- Техническое задание (Приложение А) содержит:
  - Цель, назначение, 12 задач.
  - Функциональные требования (16 методов, меню, 6 страниц).
  - Требования к аппаратному и программному обеспечению.
- Приложение Б – таблица HTTP методов (16 эндпоинтов).

## 🧪 Порядок демонстрации (что показывать преподавателю)

1. **Swagger (режим инкогнито)**  
   - Выполнить `POST /login` для `testuser` → получить `200` и `sessionid` в ответе.

2. **Swagger – список заявок** (после логина) → видны только свои заявки.

3. **Браузер (DevTools)** → вкладка Application → Cookies → скопировать `sessionid`.

4. **Insomnia**:
   - `GET /requests/` без куки → `401`.
   - `GET /requests/` с кукой `testuser` → только свои заявки.
   - `POST /add/` (добавление услуги) → `201`.
   - `PUT /update/` (ФИО) → `200`.
   - `PUT /form/` → статус `FORMED`.
   - `PUT /complete/` с кукой `testuser` → `403`.
   - `POST /login` (модератор) → копируем его `sessionid`.
   - `PUT /complete/` с кукой модератора → `200`, статус `COMPLETED`, `total_cost`.
   - `GET /requests/` с кукой модератора → все заявки.

5. **Redis (cmd)**:
   - `docker exec -it redis redis-cli -n 1 KEYS '*'` → список ключей.
   - Запуск Django shell и десериализация сессии (с `pickle.loads`) → вывод имени пользователя.
